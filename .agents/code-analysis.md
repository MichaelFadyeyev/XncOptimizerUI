# What XncOptimizerUI is

A Windows desktop app (WPF, .NET 9, MVVM) for opening, inspecting, editing, and batch-transforming `.project` XML files produced by **GibLab** CAM/nesting software (furniture/panel-cutting production). It provides a parts/bands/sheets browser with live editing, filtering, CSV/clipboard export, persisted user configuration, XNC machining-program reading and copying, groove/mill conversion, mill-traversal optimization, and dependency injection (DI) for testability.

# Domain model of the .project file (unchanged)

Root `<project>` containing `<good typeId="product">` (finished product, holding `<part>` panels: name, id, dimensions `l`/`w` plus detail/cut/trimmed size fields, `count`, edge-band refs `elt`/`elb`/`ell`/`elr` encoded as `@operation#<EL id>` and matching `*Mat` names), `<good typeId="sheet">` (raw sheet stock), `<good typeId="band">` (edge-banding material), and tool goods. Operations are flat `<operation typeId="...">` children: `XNC` (CNC drill/rout with an escaped XML `program` sub-document), `CS` (saw cut, references parts plus a trailing sheet part and `<material>`), and `EL` (edge-banding, references a `<material>` = band good).

# Architecture

## Core abstractions & services

- **Project service roles (`Contracts/`)** — all XML manipulation and file I/O goes through five interfaces, bundled for the view model as `ProjectServices(Session, Reader, Editor, Restructuring, Batch)`:
  - `IProjectSession` (`Open`/`Close`/`Save`, `FullPath`) → `Services/Project/ProjectDocument.cs`, the one shared document: typed queries (`Operations`/`Goods` by `GibLabTypes`, `XncOperationsOf(partId)`, `ProductParts()`), `AppendDescription`, `SaveAsSuffixed` (output names in `ProjectFileNames`).
  - `IProjectReader` (`ReadBands`/`ReadSheets`/`ReadProducts`/`ReadParts`, `ReadXncPrograms`, `GetXncProgramsCount`, `GetPartsWithXncTurnDiscordance`) → `ProjectReader`; every read is self-contained (no read-order dependency, no caches).
  - `IProjectEditor` (`UpdatePart`, `RotatePart`, `UpdateBore`, `UpdateVariable`; in place, the caller saves) → `ProjectEditor`, with `PartUpdater` and `Services/Xnc/XncProgramEdits.cs`; rotation geometry in `Services/Xnc/XncProgramRotator.cs`.
  - `IProjectRestructuring` (`GroupIdenticalElements`, `PrepForSplitAlongX`, `ReplaceXncPrograms`; saved as a new file) → `IdenticalPartsGrouper`, `SplitAlongXPreparer`, `XncProgramReplacer`.
  - `IXncBatchOperations` (`ConvertGroovesAndMills`, `ConvertBoresAndMills`, `OptimizeMillTraversal`, `SortToolDeclarations`, `OffsetMillPaths`, `CleanOutsideOperations`) → `Services/Xnc/Batch/`: each an `IXncBatch<TStats>` spec (`GrooveMillBatch`, ...: per-program rewrite + log texts) run by `XncBatchRunner`, which rewrites every program before writing any back, logs each part and saves a suffixed file only when something changed. Rewrites: `Services/Xnc/Conversions/GrooveMillConverter.cs`, `BoreMillConverter.cs` (shared `ConversionContext`, `ConversionTools`), `Services/Xnc/MillTraversalOptimizer.cs`, `XncToolDeclarationSorter.cs`, `MillPathOffsetter.cs` (+ `Geometry/ContourOffsetGeometry.cs`), `Outside/OutsideOperationDetector.cs` (one `IOutsideRule` per kind: `BoreOutsideRule`, `GrooveOutsideRule`, `MillOutsideRule`).
- **`OperationResult`** (`Contracts/OperationResult.cs`) — every operation returns `Changed` + log entries (built with `Services/OperationLog`); `LogText` feeds the log box (highlighted entries after `***`), `MessageText` the warning dialog when nothing changed.
- **XNC program helpers (`Services/Xnc/`)** — `XncProgramText` is the one decode/encode path of the escaped `program` attribute (keeps the `<?xml ...?>` declaration); `XncTags` element names (use them, not tag literals); `XncToolKinds` tool prefixes (`Bore`/`Cut`/`Mill`). Shared by the reader, the rewriters, the detector and the sorter: `XncAttributeParsing` (plain attribute values: `RequireDouble`, `RequireDimension`, `ParseInt`/`ParseBool`, `ParsePositionCode`, `IsClockwise`, `ArrayCount`, `ToolDiameter`/`ReadToolDiameters`), `XncSymbols` (`SeedProgramSymbols`/`DimensionSymbols`/`ProgramSymbols`/`SymbolsBefore`, the one `Eval` wrapper, `EvalPoint`, `ExpressionAttributes`, `RenameIdentifier`/`ReferencesIdentifier`), `XncNumberFormat` (`FormatNumber`/`SetNumber` for writing recalculated values); mill discovery and contour centre-line reading (`CollectMills`, `ReadPath`) in `XncMillElements.cs`. Pure geometry lives in `Services/Xnc/Geometry/` (namespace `...Services.Xnc.Geometry`): `Vec2` (the one point type; `XncPoint.ToVec2()` converts the read-only model point), `Primitive`/`OffsetLayout`, `PlanarGeometry` (`Tolerance`, intersections, `ArcCentreFromChord`, `DistanceToSegment`), `Box` (axis-aligned box, segment distance, separating-axis test), `ChordPath` (arc flattening, even-odd containment), `ContourOffsetGeometry`, and `MillShapeGeometry` (`<mr>`/`<me>` centre lines: `RoundedRectangle`, `Circle`, `EllipseChords`, `Place`, shared with the preview's `MillPreviewGeometry`). Program parsing for display: `XncProgramReader.cs` (one `Parse*` per element, dispatched by tag) + `XncExpressionEvaluator.cs` + `XncSymbolTable.cs` (see [[project-file-processing-skill]]).
- **`IConfigService`**, **`IDialogService`** — injected abstractions (formerly static/modal classes), replacing the old `ConfigService` static methods and direct `MessageBox`/`SaveFileDialog` calls with testable dependencies.
- **`Extensions/XContainersExtensions.cs`** — null-safe getters/setters for XML attributes: typed accessors (`GetLengthDecimalValue`, `GetIdIntValue`, `GetElbIdIntValue` for `@operation#<id>` parsing, `GetProgramValue`, `GetSideValue`, etc.), and mutation methods (`SetLengthValue`, `SetWidthValue`, ...) to support in-place editing.

## Domain models & presentation

- **Models** (`MVVM/Models/Part.cs`, `Band.cs`, `Sheet.cs`, `Product.cs`) — plain data classes (`Id`, `Name`, `Length`, `Width`, `Count`, sheet/banding relationships). `Product` (`Id`, `Name`, `Code`, `Count`) wraps a `<good typeId="product">` good.
- **`MVVM/Models/Xnc/`** — read-only classes representing parsed XNC programs: `XncProgram` (top-level; `Dx`/`Dy`/`Dz`, `Side`, `Turn` (0..3 orientation code) + `TurnDegrees` (×90 clockwise)), `XncTool`, `XncBore`+`BoreSurface`, `XncGrooving`, `XncMillingContour`+`XncMillingSegment` (`XncLineSegment`, `XncArcSegment`), `XncMillingRectangle`, `ToolPosition`, `XncPoint`. Format documented in [[project-file-processing-skill]].
- **ViewModels** (`PartVM`, `BandVM`, `SheetVM`, `ProductVM`, in `MVVM/ViewModels/Parts/`) — wrap domain models for data-binding (CommunityToolkit `ObservableObject`). `ProductVM` (`Id`, `Name`, `Code`, `Count`) wraps `Product` and is purely a read-only display projection — no command reads or writes it.
- **`AppViewModel.cs`** — the window shell: file lifecycle commands (Open/Save/Close), CSV/clipboard export (`Parts/PartsListText`), the window title, and one property per child view model. The children, all singletons registered by `App.AddViewModels` and sharing state through constructor injection:
  - `ActivityLog` (`Log.Text`, the log box), `ProjectWorkspace` (open file `FullPath`/`IsOpen`, `Open`/`Reopen`/`ReadItems`/`Close`), `PartEditSaver` (saves grid and program edits in place, timestamps from `TimeProvider`).
  - `Parts/ProjectCatalogVM` (`Bands`/`BandOptions`/`Sheets`/`Products`), `Parts/PartsListVM` (all/shown/checked parts, `SelectedPart` with auto-save on change, `CheckedCount`, Check all/Uncheck all; raises `SelectedPartChanged`), `Parts/PartsFilterVM` (name + range filter; `SuspendFilter()` scope while resetting).
  - `Machining/SelectedPartMachiningVM` (program tables, `Checked*` sets, `ProgramsText`, `Programs`, in-cell bore/variable edits; raises `ProgramsRead`), `Preview/PartPreviewVM` (display size, turn, sheet thickness, `Rotation`/`CanRotate`, `NeverFlipTclOnTurn`).
  - `Panels/`: `SourcePartVM`, `PreparationPanelVM` (+ `LabelsVM`), `CleanOutsidePanelVM`, `SortToolsPanelVM`, `GrooveMillPanelVM`, `BoreMillPanelVM`, `MillOffsetPanelVM`, `MillOrderPanelVM` — each holds its options and command and runs it through `BatchCommandRunner` (no-file guard, extra checks, parts selector, log, warn when unchanged, otherwise `ProjectWorkspace.Reopen`).

## Configuration & testing

- **`Services/ConfigService.cs`** + **`Configuration/AppOptions.cs`** — persists user settings as JSON at `%AppData%\XncOptimizerUI\configuration.json`: `SawWidth` (kerf width, default 4.0), `LabelsToProcess` (text labels for filtering, default `["поріз.2х40"]`), `MillingToolDiams` (default `[6, 10, 20]`), `NeverFlipTclOnTurn` (part rotation keeps edge-groove `c` like GibLab, default `false`, bound to the checkbox in the left-menu "Options" group), and the remembered last-selected label. `GroovingToolWidths` (default `[2.8, 3.2]`): the first one is the mills → grooves cutter.

View-model tests build `AppViewModel` through the app's own `App.AddViewModels` (`TestViewModels.Create`). Headless (no `MessageBox`, `SaveFileDialog`, or static config singletons). Fixture-based tests derive from `TempFixtureTestBase` (per-test temp dir + `CopyFixture`).
  - **Golden (characterization) tests** guard refactoring: `OperationGoldenTests` runs every document-changing project-service operation on fixtures and compares the saved `.project` + log with `Golden/Operations/`; `PreviewGoldenTests` lists every shape the mill/bore/groove preview renderers draw (geometry rounded to 0.001 px) against `Golden/Preview/`. A missing snapshot is created and fails; to accept an intended change run the tests with `XNC_UPDATE_GOLDEN=1` and review the `Golden/` diff (`GoldenSnapshot`).
- **Build settings** — `Directory.Build.props` (LangVersion latest, nullable as errors, `AnalysisLevel=latest-recommended`, code style enforced in build) and `.editorconfig` (conventions + analyzer tuning). The build is warning-free; keep it so. `CA2201` (`throw new Exception`) is a suggestion until specific exception types are introduced.
- **`MainWindow.xaml`** — left column: file buttons, an "Options" group (inactive "Options" button + the "Never flips TCL on program turning" checkbox), command buttons + label management, and the "Clean operations" panel under the Preparation panel. The rest of the window is a `TabControl` with two tabs, plus a log box (bottom row) spanning both.
  - **"Parts" tab**: filterable Parts `DataGrid` (row 1) over a resizable part-preview row (row 2: a scrollable `PartCanvas` viewport with a fixed axis/turn overlay, a fixed-width column of 0°/90°/180°/270° rotation buttons right of it (`MVVM/Views/PartPreview/PartRotationPanel.xaml`, radio buttons styled as toggle buttons by `RotationToggleRadioStyle` in `Resources/ControlStyles.xaml`, merged in `App.xaml`), plus a "Programs" column on its right holding Bores (X/Y/Depth editable, see "Edit bores" below)/Grooves `DataGrid`s over the `Machining.ProgramsText` `TextBox`). The Parts grid and preview row are separated by a horizontal `GridSplitter`; the preview and the Programs column are separated by a vertical `GridSplitter`. Both preview scrollbars are always visible. The part preview can be zoomed with the mouse wheel from the fit-to-view scale upward, preserving the point under the cursor, and a pressed mouse wheel pans magnified previews; splitter resizing recalculates the fit scale while preserving the relative part position, and selecting another part resets zoom and scroll position to fit-to-view. The coordinate axis and turn angle remain anchored to the preview border viewport regardless of zoom or scroll. When the selected part's `ConsiderTexture` is true, `RenderPart` draws three centered, parallel 1 px `#808080` lines over the face (length `l/3`, outer-line span `w/5`); the mark's base axis is program `dx` at turn 0, rotated by the first applied program's `turn`. Part-preview colours / line widths / metrics are `Window.Resources` keys (`PartFaceBrush`, `PartOutlineBrush`, `PartOutlineThickness`, `PartTextureBrush`/`PartTextureLineThickness`, `MinEdgeProjectionThickness`, `ProjectionGapMm` — the 10 mm face-to-side-view gap, scaled with the part, `PartPreviewMargin`, `AxisXBrush`, `AxisYBrush`, plus `BoreSideTrueBrush`/`BoreSideFalseBrush`/`BoreSelectedBrush`/`BoreOutlineThickness`/`BoreCenterLineThickness`/`BoreCenterLineOvershootMm` for the bore overlay, `ThroughCutOffsBrush`/`BlindCutOffsBrush`/`MillStripOpacity` for the mill overlay).   - **"Products & Materials" tab**: three stacked read-only `DataGrid`s — Products (Name/Code/Count), Sheets (Code/Name), Bands (Code/Name/Int. Sign/Ext. Sign, with a `SelectedBand` binding that has no further effect wired to it). No add/edit/delete; this tab is a reference view of the goods already parsed for the "Parts" tab.
  - Icon `xnc_logo.ico`.

# User-facing operations

**File lifecycle** — Open/Save/Close project XML file. Opening populates Bands, Sheets, Products, Parts grids from the parsed file and pre-selects the first part. On open only, `AppViewModel.WarnOnXncTurnDiscordance` calls `IProjectReader.GetPartsWithXncTurnDiscordance()` — any part machined by several XNC operations that disagree on `turn` pops a warning ("Discordance in xnc programs turn corner for parts: …") and each offending part name is logged. Closing clears all state. Window title shows assembly name + current filename.

**Part preview** — the half-height row under the Parts grid draws the selected part in a `Canvas` viewport: a plain rectangle plus the four side views of the part. The rectangle is sized from the **first applied XNC program's `dx`/`dy`** (already in the turned machine frame) when the part has any program, otherwise from the part's own `Length x Width`; `PartPreviewVM` exposes these as `DisplayLength`/`DisplayWidth`. Each side view is a band whose thickness is the owning sheet's `t` (`PartPreviewVM.SheetThickness`, looked up in `ProjectCatalogVM.Sheets` by `PartVM.SheetId`) and whose length is the part's size in that direction, offset from the face by a 10 mm gap; band thickness, gap and face are all drawn at one uniform scale that fits face + gap + band per side into the viewport (rescaled per part). A small X/Y axis glyph sits top-left and is **not** rotated by `turn` (screen axes stay X-horizontal / Y-vertical); the first program's turn is always shown as degrees (`0°`/`90°`/`180°`/`270°`, from `PartPreviewVM.TurnText`; `0°` when the part has no XNC program) in the bottom-right corner at 2.5x the base font size. Redrawn whenever `SelectedPart` changes, the part is rotated (see "Rotate part"), or the canvas resizes.

Bores from every applied `XncProgram` (`PartPreviewVM.Programs`) are drawn on top of the geometry by `BorePreviewRenderer.DrawBores`: a face bore (`XncBore.Surface == Face`) gets a circle + crossed center lines on the Face rectangle plus a rectangle + center line on each of the four side bands, colored by the owning program's `Side`; an edge bore (`Top`/`Bottom`/`Left`/`Right`) gets a circle + crossed center lines on the one band it was drilled from (positioned from `bore.Z`) plus a rectangle + center line on the Face rectangle. Crossed center lines remain solid through Ø8 mm and use the existing dashed style for larger bores; depth-projection center-line styling is unchanged. All five projections of one bore toggle red together on click (selection is local to the current render pass, not yet wired into `AppViewModel`). Groovings are drawn the same way by `GroovePreviewRenderer.DrawGrooves`, sharing band/Face rectangle placement math with `BorePreviewRenderer` via `PartPreviewOverlayGeometry`. Unlike a bore, a groove's perpendicular offset always measures from the target band's inner (Face-adjacent) edge regardless of the owning program's `Side` (confirmed with the user - every groove-side `AddSideRectangleRange`/`Z`-anchor call passes a literal `true`, not `program.Side`). A front-plane groove (`SideCode == 0`) gets a Face rectangle (length between its start/end points, width `t`, offset from that line per its `c` tool-position), plus orientation-aware side-band projections - the two bands parallel to the groove get a plain `dp`-deep extent projection with no center line, the two perpendicular bands get a small `t`-wide/`dp`-deep rectangle at the groove's constant coordinate with a center line (a diagonal groove falls back to extent-with-center-line on all four). An edge-plane groove (`SideCode` `1`-`4` = Left/Right/Top/Bottom) gets its true rectangle on the one band it belongs to, offset from the band's inner edge by its own `Z` attribute (not by its `Start`/`End` coordinate, which is just the panel-edge value); a `dp` rectangle (no center line) on the Face rectangle; and a small `t`-wide/`dp`-long marker (with a center line) on each of the two bands perpendicular to its own plane - flush at its own fixed edge coordinate along its intrinsic depth axis, and displaced from *that target band's* inner edge by the groove's own `Z` (same formula/helper as its own-band rectangle). Grooves are also still shown in the "Grooves" `DataGrid` (below), whose Side column uses the same `SideCode` 1=Left/2=Right/3=Top/4=Bottom mapping. Mills - `<ms>` contours, `<mr>` rectangles, `<me>` ellipses - are drawn first, on the Face rectangle only, by `MillPreviewRenderer.DrawMills` (bores and grooves then go on top). Each mill's centre line is put in travel order (`fwd="true"`: open paths as authored, closed `<ms>` contours counter-clockwise, `<mr>`/`<me>` clockwise - in the operator's view, which is the Y-down preview itself; `fwd="false"` reverses each). Per `c`: `0` keeps both sides (no fill); `1`/`2` (tool right/left of travel; for a closed `<ms>` contour right/left of its declared segment order instead, regardless of `fwd` - declared counter-clockwise on screen puts `c=1` outside and `c=2` inside, see `xnc-program-format.md` §6.4) fill the part area on the tool side with `ThroughCutOffsBrush` when the mill's deepest `dp >= dz`, else `BlindCutOffsBrush` - for a closed mill that is its inside or outside, for an open mill whose both ends are on/beyond the outline it is the part on that side (centre line extended along its end tangents), and an open mill ending inside the part gets no fill; `3` (pocket) fills its inside. On top: the swept strip (tool path stroked one tool Ø wide with round caps, `PartFaceBrush` at `MillStripOpacity`), the centre line (`PartOutlineBrush`/`PartOutlineThickness`, like the part ridges), the tool-centre path (centre line offset by Ø/2 to the tool side through the shared `Services/Xnc/Geometry/ContourOffsetGeometry.cs`, the same geometry "Offset mill path" uses; 1px, 3px dash, program-`Side` brush) and a face-bore-style Ø circle with crossed centre lines (solid through Ø8 mm and dashed above Ø8 mm, matching bore crosshairs) at the tool path's start (`<mr>`: middle of its local `y-` side, `<me>`: local `y-` end of its `w` semi-axis, both turned by `a`, positive = clockwise on screen - confirmed with the user). Clicking a mill's strip, lines or marker toggles all its lines red. Banding is not rendered; see `.agents/todos.md` for what's still deferred.

**Edit bores** — the Bores table (`MVVM/Views/PartPrograms/SelectedPartBoresGrid.xaml`, `SelectedItem` → `SelectedPartMachiningVM.SelectedBore`) edits X / Y / Depth in place, entered natively like the Parts grid (click on the selected cell or F2). Display cells show the evaluated value (rounded, `MachiningNumber`); hovering a cell whose attribute is authored as an expression or variable shows `expression = exact value` (e.g. `throughBoreDepth = 20`; `BoreRowVM.XToolTip`/`YToolTip`/`DepthToolTip`, `null` = no tip for a plain number; `ExpressionCellTextStyle` makes the whole cell hit-testable); the editor (`ExpressionCellEditBoxStyle`, `Resources/ControlStyles.xaml`) shows the authored attribute text (`XncBore.XText`/`YText`/`ZText`/`DepthText`) and accepts a number or an expression of the program's symbols - `dx`/`dy`/`dz` plus every declared `<var>` (`XncSymbols.ProgramSymbols` from `XncProgram.Variables` in the row, `SeedProgramSymbols` in `UpdateBore`) - validated live by `Services/Xnc/BoreExpression.cs` (digits, one `.` per number, `+ - * /`, parentheses, sign only first or after `(`, finite, depth > 0; text equal to the committed authored value is never re-validated, so an untouched cell cannot block the row) - invalid text is red with the reason as tooltip and the cell cannot be committed (Esc reverts). The cell is committed on Enter, Tab, a click on another cell or focus moving to another control (DataGrid itself), and on a click anywhere else in the window, e.g. the preview (`CommitToRow` watches the window's `PreviewMouseDown`; an invalid draft is reverted then). Covered end-to-end by `XncOptimizerUI.Test/BoresGridEditingUiTests.cs` (real grid in an off-screen STA window). Columns map to attributes by surface (`BoreAttributes`, `MVVM/Models/Xnc/BoreAttribute.cs`): face `x`/`y`, Top/Bottom `x`/`z`, Left/Right `z`/`y`, all `dp`. Each cell commit goes through `Helpers/DataGridCellEditBehavior.CommitToRow` → `BoreRowVM` (`ICellEditableRow`, `INotifyDataErrorInfo`) → `SelectedPartMachiningVM.OnBoreRowEdited` → `IProjectEditor.UpdateBore(operationId, boreIndex, attribute, text)` (bore located by `XncProgram.OperationId` + `XncBore.Index`; text written as typed, `z` drops `m="true"`) → `SaveProject()` in place + log line. Rows are then refreshed **in place** (`RefreshBoresInPlace`: re-read programs, `row.Apply`, `CheckedBores` entries swapped) - replacing `Bores` inside `CellEditEnding` would throw, and in-place rows keep selection and checkboxes; the re-read programs redraw the preview.

**Edit variables** — the "Variables" tab (after "Tools"; `MVVM/Views/PartPrograms/SelectedPartVariablesGrid.xaml`, rows `SelectedPartMachiningVM.Variables` of `VariableRowVM`) lists every `<var>` of the selected part's programs (`XncProgram.DeclaredVariables`: #, Side, Name, Type, Expr, Value, Comment) and edits Name / Type / Expr / Comment in place like the bores table (same `CommitToRow` behavior, red `ValidatedCellEditBoxStyle` editors). Type is plain text that builds a `VariableTypeComboBoxStyle` selector (int/double/string/bool) only in edit mode, opening its list on load and committing when it closes - like the Parts grid band cells. Rules (`Services/Xnc/XncVariableRules.cs`, numeric part shared with bores via `Services/Xnc/NumericExpression.cs`): name = letter then letters/digits/`_`/`.`, unique, not built-in; expr by type (numeric expression over dx/dy/dz + earlier numeric vars, whole for int, true/false for bool, any text for string); a type change must fit the current expr. Commit → `SelectedPartMachiningVM.OnVariableRowEdited` → `IProjectEditor.UpdateVariable` (rename rewrites all references; a referenced var cannot become string/bool) → save in place; `RefreshAfterVariableEdit` rebuilds every other table and the preview (a var may drive bores/mills) while updating variable rows in place. Bore and variable rows share `EditableRowVM` (drafts, per-draft errors, commit/cancel). Covered by `VariableRowVMTests`, `ProjectServicesTests.UpdateVariable_*` and `VariablesGridEditingUiTests` (real grid, shared `ProgramGridUiTestBase`).

**Rotate part** — the four toggle-style radio buttons next to the preview (`PartRotationPanel`) bind TwoWay to `PartPreviewVM.Rotation` (`PartTurn` enum `Deg0..Deg270` = `turn` 0..3). Selecting a part syncs the buttons to its first program's `turn` without rotating (guarded by `_isSyncingRotation`); the panel is disabled when the part has no XNC program (`CanRotate`). Clicking a button calls `UpdatePart` (pending grid edit) + `IProjectEditor.RotatePart(partId, turn)`, then `SaveProject()` **in place** (no suffixed file), logs the new angle, and re-reads the programs via `SelectedPartMachiningVM.Refresh` so the preview (reset to fit-to-view on a turn change) and all machining tables update. A failed rotation restores the previous button. `RotatePart` sets every operation of the part to the absolute turn and rotates each program from its own turn — clockwise quarter steps `(x, y) → (dy − y, x)` with `dx`/`dy` swapped, origin kept top-left; edge bores/edge grooves move to the next edge clockwise (`bt→br→bb→bl`, `p` `3→2→4→1`); edge grooves keep start ≤ end (points swapped, as GibLab does) and flip `c` Right/Left where their per-plane travel convention reverses — unless the "Never flips TCL on program turning (keep GibLab behavior)" checkbox under the (still inactive) "Options" button in the left menu, both inside a `MenuGroupBorder` border (`PartPreviewVM.NeverFlipTclOnTurn`, persisted as `AppOptions.NeverFlipTclOnTurn`, default off) is checked, which reproduces GibLab's never-flip behavior (a GibLab bug, per the user); `<mr>`/`<me>` swap `l`/`w`; changed coordinates are written as numbers, other values keep their text with `dx`/`dy` identifiers swapped on odd turns. Full rules in `xnc-program-format.md` §6.9.

**Parts grid + filter + edit** — lists every part (checkbox, number, length/width/count, Txt, one edge-band select per edge, name). A "Checked no:" / "Filtered no:" pair above the grid shows how many parts are checked across the whole project (the set batch commands like Convert grooves/mills act on) versus how many pass the current filter; "Check all" / "Uncheck all" buttons act on the currently filtered set. Filtering is a **range** filter: `LengthMin`/`LengthMax`/`WidthMin`/`WidthMax` (each validated as a decimal by an active `DecimalValidationRule`, inclusive bounds, an empty bound is unbounded) plus `FilterName` (substring match on the part name, no validation). Typing a min above the current max (or vice versa) snaps the *other* edge to match, debounced so it reacts to the finished value rather than each keystroke (`PartsFilterVM.NormalizeRangeBounds`). "Filter"/"Clear" buttons apply/reset explicitly, but every field also re-filters live as it changes. A "Txt" checkbox column (between Count and Top Band) shows/edits `PartVM.ConsiderTexture` (`<part txt>`). Each Top/Bottom/Left/Right Band column shows plain text `<internal symbol> <band name>` (`BandOptionVM.Caption`, resolved from `PartVM.*BandingId` + `ProjectCatalogVM.BandOptions` by `Helpers/BandCaptionConverter`, also as tooltip; style `BandCaptionTextStyle`) and builds its `ComboBox` (`BandSelectComboBoxStyle` in `Resources/ControlStyles.xaml`) only in edit mode (`CellEditingTemplate`) - a heavy ComboBox per cell made grid refreshes lag. Edit mode is entered natively by DataGrid (first click selects the row, a second click on the selected cell or F2 begins editing); the ComboBox then opens its drop-down immediately, and closing the drop-down commits the cell back to text (`Helpers/DataGridCellEditBehavior.OpenDropDownOnLoad`). A custom single-click-edit behavior was removed: it set `DataGridRow.IsSelected` itself, which under Extended selection added the row instead of replacing the selection. The ComboBox lists `ProjectCatalogVM.BandOptions` (`BandOptionVM`: an empty option, then one entry per EL operation) (same `Caption` text), and binds `SelectedValue` to `PartVM.*BandingId` (EL operation id, `null` = unbanded). The Parts grid recycles row containers (`VirtualizationMode="Recycling"`). On-grid editing of Name/Length/Width persists via `UpdatePart` (which sync's the part name with its XNC operation's group-code prefix `[01]` if present) and auto-saves when the selection moves to another part; Txt and band changes are saved immediately (`PartEditSaver.SavePendingEdits`, triggered from `PartsListVM.OnPartPropertyChanged`), so they never wait for the selection-change save (clicking the Txt checkbox does not select its row). For bands `UpdatePart` rewrites each edge's `elX="@operation#<id>"` + `elXMat` (band good name) or removes both, adds/removes the part's `<part id>` in every EL operation's list (inserted in id order) so each operation lists exactly the parts using it on some edge, and recalculates the joint size `jl = l − t(ell) − t(elr)`, `jw = w − t(elt) − t(elb)` (band good `t`; also on every Name/size/Txt save). EL `elLength` and band goods' `count` are not recalculated (GibLab does that).

**XNC program display** — when a part is selected, its XNC programs (one per machined face) render in the "Programs" box as multi-line human-readable summaries:
```
Programs: 1
  /xnc/front/dx1380 dy600 dz19
  /tool/front/Bore8 Ø8
  /bore/front/Left Bore8 (0,65,10) dp34
  /groove/front/Cut3.2 (-10,565)-(1390,565) dp4 w10 Center
  /mill/front/Mill6 (250,382.5) dp21 Left 2 arc
```
Implemented via `ReadXncPrograms(int partId)` → `XncProgramReader.Read()` which parses the escaped XML `program` sub-document. Format documented in [[project-file-processing-skill]].

The selected-part panel uses three equal-width tabs: "Operations" exposes read-only
`DataGrid`s for bores, grooves, milling contours, elliptical mills, and rectangular
mills/pockets; the ellipse and rectangle grids have checked-row support and display the
requested center, size, angle, TCL, and corner-radius fields; contours contain only
segment-based milling (`<ms>` plus `<ml>`/arc elements), while `<me>` and `<mr>` are shown
in their dedicated grids. "Tools" exposes the tools table; "Variables" exposes the `<var>` declarations (see "Edit variables" below); and "XNC list" exposes the text summary, which also lists each `<var>` as `name type = expr (= value) // comment`.
`SelectedPartMachiningVM.Grooves` is flattened and numbered in XNC program/document order through
`GrooveRowVM`. Groove rows display start/end coordinates, depth, width, and the
`ToolPosition` center-line relation. Their side is derived from groove `p`: `0` maps to
Front/Back from the XNC operation `side`, while `1`/`2`/`3`/`4` map to Right/Left/Top/Bottom.
The groove grid uses extended full-row selection. `XncGrooving.SideCode` preserves the parsed
`p` value (missing `p` defaults to `0`).

**Replace XNC programs** — source part's drill programs (one per face: front/back) are validated, then copied to selected target parts. Before copying, all targets are checked for: (1) identical dimensions & banding, (2) same number of XNC faces, and (3) matching face/turn orientations. If validation passes, the `program` attribute and `countBore` metadata are overwritten, and the file is saved with the `_ren.project` suffix (or a numbered collision suffix) with an audit description. Implemented in `IProjectRestructuring.ReplaceXncPrograms(Part sourcePart, IList<Part> targetParts)` with detailed validation and error logging.

**Convert grooves ⇄ mills** — for the parts **checked** in the Parts grid (the
`PartVM.IsSelected` column), rewrites every XNC program in the chosen direction. The service
also accepts a `processPockets` flag. *Grooves → Mills*: an axis-parallel primary-pass `<gr>`
(`p="0"` or absent) with an exact configured milling-tool diameter becomes a single-segment
`<ms>` + `<ml>` contour. An off-size groove becomes a rectangular pocket using the smallest
configured cutter when that cutter fits; otherwise it is ignored. Edge-reaching contour
endpoints overshoot by half the relevant cutter diameter. Secondary-pass and diagonal grooves
remain untouched. Generated milling tools use the conversion-specific `Mill<diameter>` name.
An existing tool with the same diameter but an unrelated name (for example `Bore8`) is not
reused; a separate `Mill8` declaration is created. Existing matching `Mill...` declarations
are reused. *Mills → Grooves*: a shallow, axis-parallel, single-straight-segment
non-pocket contour is converted and its outside endpoints are clamped to the outline. With
`processPockets`, supported axis-parallel rectangular `<mr>` pockets and rectangular contour
pockets are converted too. Generated grooving tools use `Cut<diameter>` (currently `Cut2.8`);
unrelated same-diameter tools are preserved and not reused. The grooving cutter is the first
`AppOptions.GroovingToolWidths` entry (default 2.8 mm; an empty list cancels). Non-compliant elements are
left untouched and tallied as ignored; logs include converted/ignored and tools
added/removed counts. Nothing converted ⇒ returns `false`, saves nothing. Output is
`_gm.project` with collision numbering and an audit description.
`IXncBatchOperations.ConvertGroovesAndMills(IList<Part> parts, GrooveMillDirection direction, bool processPockets)`.

**Convert bores ⇄ mills** — for the parts **checked** in the Parts grid, rewrites every XNC
program in the chosen direction. *Bores → Mills*: each face bore (`<bf>`) whose tool diameter
exceeds 34 mm is milled out with a fixed 6 mm cutter (`Mill6`, created if absent) — by default
a closed four-arc contour (`<ms fwd="true">` entry at the circle's top `(cx, cy-r)` + four
`<mac dir="false">` quarter arcs about the bore centre to its left, bottom, right and back to the
top — declared counter-clockwise on screen), or a single elliptical mill (`<me>` with
`l = w = radius`, `fwd="true"`, i.e. clockwise) when the "as ellipses" checkbox is set. A through
bore keeps the tool inside the hole (`c="2"` for the counter-clockwise contour, `c="1"` for the
ellipse); a blind bore is milled as a pocket (`c="3"`) — in both forms. The mill depth equals the bore depth.
Smaller bores and edge bores are left untouched. *Mills → Bores*: a round mill — an `<ms>` entry plus ≥ 2 arc
segments (`<mac>` or radius-defined `<ma>`) that share one centre and radius and close onto the
entry point, or an `l == w` `<me>` ellipse — with diameter > 34 mm becomes a face bore, cut
with a `Bore<diameter>` tool (created if absent, e.g. `Bore40`). Orphaned tools are dropped.
Nothing converted ⇒ returns `false`, saves nothing. Output is `_bm.project` with collision
numbering and an audit description.
`IXncBatchOperations.ConvertBoresAndMills(IList<Part> parts, BoreMillDirection direction, bool useEllipse)`.

**Group identical elements** — (originally "Optimize") clusters XNC operations by: program content + edge-band materials. Groups are renumbered, consolidated into one product good, saved as `_opt.project`. Guards against re-running on already-optimized files or files with no XNC operations (logs warning instead of silently no-op'ing).

**Optimize mill traversal** — for checked parts, re-sequences eligible one-segment,
axis-parallel milling contours per XNC face and tool using a greedy nearest-neighbour walk,
reversing passes as needed to form a serpentine path. Arcs, multi-segment contours, pockets,
and `<mr>` rectangles remain in place and are counted as ignored. Nothing reordered ⇒ returns
`false`, saves nothing. Output is `_mo.project` with collision numbering and an audit description.

**Sort tools** — for checked parts, or, when the "Apply globally / filtered" checkbox under the
button is set (`SortToolsPanelVM.SortToolsGlobally`, off by default, not persisted), for every part
the grid shows (`PartsListVM.Parts`: the filtered set, all parts when no filter is set),
checked or not - a checked part hidden by the filter is then left out; moves every `<tool>` declaration of each XNC program to
the program start (before `<var>`s and every element using it), ordered by kind from the name
prefix (`Bore` - `Cut` - `Mill`, case-insensitive, other names last; kind follows the name, not
the use - a `Bore10` cutting an `<ms>` still ranks as a bore), then by `d` ascending, then by
name. Repeated identical declarations collapse into the first one. A program is skipped
(untouched, reason logged) when one tool name is declared with different `d` values, a `d` is
not numeric, or a `<tool>` sits between a contour element and a following segment (removing it
would join the segments to the previous contour). Nothing reordered ⇒ returns `false`, saves
nothing. Output is `_to.project` with collision numbering and an audit description.
`IXncBatchOperations.SortToolDeclarations(IList<Part> parts)` →
`Services/Xnc/XncToolDeclarationSorter.SortInProgram`.

**Offset mill path** — for checked parts, shifts every mill in every XNC program by the
distance typed next to the "Offset mill path" button (mm, > 0) to the right (`R`) or left (`L`)
of its traversal direction. Two checkboxes under the input ("open paths", "closed paths / rect. /
ellipses", both on by default) choose which mills are processed; unselected ones are left
untouched and logged as skipped (none selected ⇒ nothing runs). Direction comes from the mill head's `fwd` (absent = `true`): closed
`<ms>` contours (pockets included) travel counter-clockwise for `true`, clockwise for `false`;
`<mr>` and `<me>` (pockets included) the opposite - clockwise for `true`; open contours travel in authored order for `true`, reversed for `false`. Arc `dir` is geometry
only (`true` = clockwise sweep); clockwise/right are the operator's view, i.e. the raw XNC frame
mirrored in Y. `<ms>` contours get every entry/segment end recalculated: lines shift along
their normal, arcs keep their centre and change radius (`<ma>` `r` updated), corners meet at the
offset pieces' intersection, and a convex corner whose mitre would reach beyond 4× the offset is
bridged by an inserted `<mac>` round-join. Open-path ends on or beyond the outline keep their
perpendicular distance from the crossed edge (e.g. `x="-10"` stays); ends inside the part move
perpendicularly. `<mr>`: `l`/`w` ± 2×offset, `r` ± offset (never below 0); `<me>`: semi-axes
± offset. Unchanged values keep their authored text (`dx+10`); changed ones are written as
numbers rounded to 4 decimals. Mills that don't resolve, reverse, or collapse are left untouched
and counted as ignored. Nothing offset ⇒ returns `false`, saves nothing. Output is
`_off.project` with collision numbering and an audit description.
`IXncBatchOperations.OffsetMillPaths(IList<Part> parts, double offset, MillOffsetSide side, MillPathKinds kinds)`.

**Clean operations (remove outside operations)** — the "Clean operations" panel right under the
Preparation panel (button, "Clean outside:" label, "Bores" / "Grooves" / "Mills" checkboxes, all on
by default - `CleanOutsidePanelVM.CleanOutsideBores`/`Grooves`/`Mills`, not persisted) removes, from the
**checked** parts or from **every part of the project when none is checked** (the filter is
ignored), each XNC element of the selected kinds that lies outside the part volume
`[0, dx] x [0, dy] x [0, dz]` and never intersects it (touching a face counts as outside).
Geometry (`Services/Xnc/Outside/`: `OutsideOperationDetector` + `BoreOutsideRule`/`GrooveOutsideRule`/`MillOutsideRule`, raw program frame): bores are judged by their
centre only (confirmed with the user - outside when the centre is outside the contour, whatever the
tool Ø; a centre on a side stays): face bore `bf` = centre (every hole of an `ac`/`as`/`av` array) vs
the face; edge bore `bl`/`br` (`bt`/`bb`) = centre `y` (`x`) / `z` (`dz/2` for `m="true"`) vs the
`dy` (`dx`) x `dz` edge; face groove
(`p="0"`) = its `t`-wide footprint placed by `c` like the preview, separating-axis test vs the face;
edge groove (`p` 1..4) = its span along the edge, or the band `z ± t` (c ignored - never narrower than
the cut) through the thickness; mills (`<ms>` + segments, `<mr>`, `<me>`) = a closed pocket
(`c="3"`) only the area inside its contour (a pocket whose side lies on a part side is outside), any
other mill everything within Ø/2 of its tool-centre path - the centre line for `c="0"`, the centre
line shifted Ø/2 to the tool side for `c="1"`/`"2"` (`ContourOffsetGeometry.TryOffset` without an
outline; sides as the preview places them; Ø around the centre line if the shift collapses), so a
mill on a part side with its tool on the outer side is outside; arcs/ellipses are flattened to
chords and the chord error is added.
Elements with `dp <= 0` are kept; elements that don't resolve (unknown tool, bad expression,
degenerate shape, edge-bore array) are kept and counted as "unresolved". A removed `<ms>` takes its
segments along; tools left unreferenced are dropped (`RemoveUnreferencedTools`). Every removed element
is logged as authored (`Clean: "part" (id=…), XNC id=…: removed <bf x="-5" … /> [+ N segment(s)]`),
then a per-part and a total summary. Nothing removed ⇒ returns `false`, saves nothing. Output is
`_cln.project` with collision numbering and an audit description. `countBore` is not recalculated
(like the other conversions). Lead-in/out moves (`in`/`out`/`sxy`) are not modelled.
`IXncBatchOperations.CleanOutsideOperations(IList<Part> parts, OutsideOperationKinds kinds)`;
covered by `CleanOutsideOperationsTests` on `TestData/td-clean-outside.project` and `AppViewModelTests.CleanOutsideOperations_*`.

**Prep for split along X** — two variants (same core algorithm): (1) hardcoded text label `"_поріз.2х40мм"` (button 1), (2) user-selected label from config (button 2). Algorithm: double width by `2× + SawWidth`, halve count rounding up, double/mirror the drill program's bores. Saw-kerf width is configurable via `ConfigService.SawWidth` (injected, default 4.0). The part's XNC operations are found by part id; saved as `_spl.project` (`SplitAlongXPreparer`).

**Export parts list** — builds tab- or semicolon-separated list (length, width, count, banding external symbols, name) with blank separator row after parts on sheets named `"Сращ.(2)"` (spliced/joined marker). Outputs to CSV file or clipboard.

**Bands external symbols** — for display/export, each distinct band material's XML `elSymbol` is mapped to A–Z "external symbol" (ordered by thickness) via `ReadBands()`.

**Products & Materials tab** — a second top-level tab, separate from the Parts/preview tab, showing three read-only reference grids populated on open by `ProjectWorkspace.ReadItems()`: Products (`<good typeId="product">` goods, via `ReadProducts()`/`ProductVM`: Name/Code/Count), Sheets (Code/Name), and Bands (Code/Name/internal+external symbol). Nothing here is editable or exported from directly — it exists to let the user inspect what goods a file declares alongside the Parts grid.

The selected-part Programs panel uses three equal-width tabs: "Operations" contains
read-only tables for bores, grooves, milling contours, elliptical mills, and rectangular

**Adding features:**
- Business logic lives in the project services (`Services/Project`, `Services/Xnc`) behind the role interfaces in `Contracts/`. Add a method to the fitting role interface first, then implement it; return an `OperationResult`. A new rewrite of the selected parts' XNC programs is a new `IXncBatch` spec run by `XncBatchRunner`.
- Tests must not be modal or disk-dependent — use `FakeProjectService` and NSubstitute mocks; inject `TimeProvider` for deterministic timestamps.
- UI commands are methods in the view model that owns the area (`AppViewModel` for the file commands, a `Panels/` VM per menu group, ...) decorated with `[RelayCommand]` (from `CommunityToolkit.Mvvm`). Bind them in XAML with `Command="{Binding CommandName}"` under a `DataContext` set to that child (e.g. `{Binding MillOffset}`). A new view model is registered in `App.AddViewModels`; a new batch command goes through `BatchCommandRunner`.
